# 需求文档

## 简介

本文档规定了基于 macOS 的 OpenHarmony 分布式相机系统构建和测试框架的需求。该框架使开发者能够在 macOS 上编译、测试和调试分布式相机源代码，而无需 OpenHarmony 硬件设备。该系统通过 stub/mock 层模拟 OpenHarmony 系统依赖，同时保持与原始平台的 API 兼容性。

## 术语表

- **Build_System（构建系统）**：基于 CMake 的编译基础设施，将源代码转换为可执行库
- **Source_Service（源服务）**：分布式相机控制器服务（SA_ID=4803），用于管理控制设备上的相机操作
- **Sink_Service（受控服务）**：分布式相机受控服务（SA_ID=4804），用于在受控设备上提供相机访问
- **Stub_Layer（Stub 层）**：macOS 平台适配层，提供 OpenHarmony 系统 API 的 mock 实现
- **External_Dependencies（外部依赖）**：编译所需的 21 个 OpenHarmony 代码仓库集合
- **Channel_Module（通道模块）**：分布式相机数据传输的三通道通信系统（控制/快照/连续）
- **Data_Process（数据处理）**：相机流的编码/解码和数据处理管道
- **Camera_Client（相机客户端）**：受控设备上的本地相机访问组件
- **HDF_Virtual_Camera（HDF 虚拟相机）**：源设备上的虚拟相机驱动组件
- **Dynamic_Library（动态库）**：编译输出文件（libdcamera_source.dylib 和 libdcamera_sink.dylib）
- **Property_Test（属性测试）**：验证随机生成输入的通用属性的测试
- **Unit_Test（单元测试）**：验证特定示例和边界情况的测试

## 需求

### 需求 1：构建系统配置

**用户故事**：作为开发者，我希望在 macOS 上配置构建系统，以便无需手动设置即可编译 OpenHarmony 分布式相机代码。

#### 验收标准

1. 当开发者运行 CMake 配置时，**构建系统**应检测 macOS 平台并应用相应的编译器标志
2. 当外部依赖缺失时，**构建系统**应报告哪些仓库不可用，并继续使用可用组件
3. **构建系统**应使用 C++17 标准和 Clang 编译器
4. **构建系统**应定义平台宏（__APPLE__、__MACOS__、DCAMERA_LOCAL_TEST）用于条件编译
5. 当解析 include 路径时，**构建系统**应优先级 stub > include > OHOS 源 > external 目录

### 需求 2：源服务编译

**用户故事**：作为开发者，我希望编译源服务（SA 4803），以便在 macOS 上测试相机控制器功能。

#### 验收标准

1. 当编译源服务时，**构建系统**应生成 libdcamera_source.dylib
2. **构建系统**应包含来自 base、sourceservice、state machine 和 common 模块的所有必需源文件
3. 当编译 OpenHarmony 源文件时，**构建系统**不应修改原始源代码
4. **构建系统**应链接 cJSON 静态库和 C++ 标准库
5. 当编译完成时，**动态库**应导出 OpenHarmony 接口中定义的所有公共 API 符号

### 需求 3：受控服务编译

**用户故事**：作为开发者，我希望编译受控服务（SA 4804），以便在 macOS 上测试相机提供者功能。

#### 验收标准

1. 当编译受控服务时，**构建系统**应生成 libdcamera_sink.dylib
2. **构建系统**应包含受控服务入口点和必需的依赖项
3. **动态库**应可独立加载，无需源服务依赖
4. 当编译完成时，**动态库**应导出受控操作的所有公共 API 符号

### 需求 4：OpenHarmony 系统 API Mock

**用户故事**：作为开发者，我希望在 macOS 上 mock OpenHarmony 系统 API，以便代码可以在没有 OpenHarmony 运行时依赖的情况下编译和运行。

#### 验收标准

1. 当调用 OpenHarmony 系统 API 时，**Stub 层**应提供 mock 实现，返回成功（0）用于模拟
2. **Stub 层**应保持与 OpenHarmony 接口的 API 签名兼容性
3. 当包含 stub 头文件时，**构建系统**应优先考虑系统 API 的 stub 实现而非 OpenHarmony 头文件
4. **Stub 层**应 mock HiLog、IPC、系统能力管理器和设备管理器 API
5. 当调用 mock 函数时，**Stub 层**应记录调用以用于调试目的

### 需求 5：外部依赖管理

**用户故事**：作为开发者，我希望正确集成 OpenHarmony 外部依赖，以便分布式相机代码可以访问所需的类型和接口。

#### 验收标准

1. **构建系统**应引用 external 目录中的 21 个 OpenHarmony 代码仓库
2. 当存在外部仓库时，**构建系统**应包含来自 c_utils、IPC、hilog、safwk 和 distributed_hardware_fwk 的头文件
3. 当外部仓库缺失时，**构建系统**应发出警告但继续使用可用组件编译
4. **构建系统**不应修改 external 仓库中的文件
5. 当发生头文件冲突时，**构建系统**应优先考虑外部仓库头文件而非 stub 头文件用于类型定义

### 需求 6：通道模块集成

**用户故事**：作为开发者，我希望编译三通道通信系统，以便测试控制、快照和连续数据通道。

#### 验收标准

1. **构建系统**应包含来自 services/channel 目录的通道模块源文件
2. 当编译通道接口时，**构建系统**应包含 icamera_channel_listener.h 和相关头文件
3. **构建系统**应编译用于 all-connect 场景的协作管理器 CAPI 接口
4. 当通道代码引用 softbus API 时，**Stub 层**应提供 mock 实现

### 需求 7：数据处理管道编译

**用户故事**：作为开发者，我希望编译数据处理管道，以便测试编码、解码和流处理功能。

#### 验收标准

1. **构建系统**应包含来自 services/data_process 目录的数据处理源文件
2. 当编译数据处理模块时，**构建系统**应包含 pipeline、interfaces 和 utils 头文件
3. **构建系统**应编译流数据处理和 feeding smoother 组件
4. 当引用 codec API 时，**Stub 层**应提供 av_codec 接口的 mock 实现

### 需求 8：单元测试支持

**用户故事**：作为开发者，我希望编写和运行单元测试，以便验证特定功能和边界情况。

#### 验收标准

1. **构建系统**应支持与 C++ 单元测试框架集成
2. 当执行单元测试时，**构建系统**应将测试可执行文件链接到编译的动态库
3. **构建系统**应提供初始化 mock 环境的测试固件
4. 当测试访问 mock API 时，**Stub 层**应返回可预测的值用于断言
5. **构建系统**应生成测试报告，显示每个测试用例的通过/失败状态

### 需求 9：基于属性的测试支持

**用户故事**：作为开发者，我希望编写基于属性的测试，以便在大量生成的输入上验证通用正确性属性。

#### 验收标准

1. **构建系统**应支持与 C++ 基于属性的测试库集成
2. 当执行属性测试时，**构建系统**应运行每个属性测试至少 100 次迭代
3. 当属性测试失败时，**构建系统**应报告违反属性的失败输入
4. **构建系统**应提供生成器用于创建随机有效的相机配置、事件和命令
5. 当属性测试通过时，**构建系统**应确认属性在所有生成的测试用例中成立

### 需求 10：构建产物管理

**用户故事**：作为开发者，我希望构建产物有组织且可安装，以便轻松部署和测试库。

#### 验收标准

1. 当编译成功时，**构建系统**应将动态库放置在构建输出目录中
2. **构建系统**应提供安装目标，将库复制到标准位置
3. 当安装库时，**构建系统**应保留库依赖和链接信息
4. **构建系统**应生成调试符号用于调试支持
5. 当执行清理操作时，**构建系统**应移除所有生成的产物而不影响源代码

### 需求 11：错误处理和诊断

**用户故事**：作为开发者，我希望在编译期间获得清晰的错误消息，以便快速识别和修复构建问题。

#### 验收标准

1. 当源文件缺失时，**构建系统**应报告特定文件路径并继续使用可用文件
2. 当找不到头文件时，**构建系统**应报告缺失的头文件和包含它的文件
3. 当链接失败时，**构建系统**应报告未定义的符号并建议可能缺少的 stub 实现
4. **构建系统**应显示配置状态摘要，显示已找到和缺失的依赖项
5. 当发生编译警告时，**构建系统**应显示它们而不将其视为错误

### 需求 12：API 兼容性验证

**用户故事**：作为开发者，我希望验证与 OpenHarmony 的 API 兼容性，以便在 macOS 上测试的代码在目标平台上工作。

#### 验收标准

1. 当创建 stub 实现时，**Stub 层**应完全匹配 OpenHarmony API 签名
2. 如果 stub 签名与 OpenHarmony 头文件不匹配，**构建系统**应使编译失败
3. 当添加新的 OpenHarmony API 时，**构建系统**应报告缺失的 stub 实现
4. **构建系统**应验证动态库中导出的所有符号与 OpenHarmony 接口规范匹配
5. 当运行 API 兼容性测试时，**构建系统**应验证函数签名、参数类型和返回类型

### 需求 13：增量构建支持

**用户故事**：作为开发者，我希望增量构建正确工作，以便在开发期间快速迭代。

#### 验收标准

1. 当修改源文件时，**构建系统**应仅重新编译受影响的文件及其依赖项
2. 当修改头文件时，**构建系统**应重新编译所有包含它们的文件
3. 当修改 stub 实现时，**构建系统**应重新编译和重新链接受影响的库
4. **构建系统**应准确跟踪依赖关系以避免不必要的重新编译
5. 当未检测到更改时，**构建系统**应跳过编译并报告目标是最新的

### 需求 14：调试和发布构建模式

**用户故事**：作为开发者，我希望以调试或发布模式构建，以便针对调试或性能进行优化。

#### 验收标准

1. 当选择调试模式时，**构建系统**应使用 -g -O0 标志编译并启用所有调试符号
2. 当选择发布模式时，**构建系统**应使用 -O2 -DNDEBUG 标志编译并针对性能进行优化
3. **构建系统**应允许在调试和发布模式之间切换而无需完全重新构建
4. 当调试模式激活时，**构建系统**应启用额外的运行时检查和断言
5. 当发布模式激活时，**构建系统**应剥离不必要的符号以减少库大小

### 需求 15：文档和示例

**用户故事**：作为开发者，我希望有文档和示例，以便了解如何使用构建系统和测试框架。

#### 验收标准

1. **构建系统**应提供 README 文档，记录构建先决条件和设置步骤
2. **构建系统**应包括示例单元测试，演示如何测试相机操作
3. **构建系统**应包括示例属性测试，演示如何验证正确性属性
4. **构建系统**应记录 stub 层架构以及如何添加新的 mock 实现
5. **构建系统**应提供常见构建错误的故障排除指南
